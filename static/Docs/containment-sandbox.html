Containment and Sandboxing in Aether

Background

The Principles of Containment state: the container can see the contained, but the contained cannot casually reach the container. Each boundary is an implicit sandbox, and these should be nestable with each level further restricted.

This pattern appears in:

  • Dependency Injection containers (PicoContainer, Spring)
  • Virtual Machines (VMware, EC2)
  • Docker containers (namespaces, cgroups)
  • Java's SecurityManager + ClassLoader hierarchies
  • UI component trees (Swing, the DOM)

Aether's builder DSL with closures provides the language-level mechanism for this: trailing blocks for declarative structure, closures for isolation boundaries, and a permissions context that flows inward but cannot be reached outward.

What to contain

A sandbox restricts access to system capabilities. These fall into categories:

The outermost scope starts with no permissions (deny-all) or all permissions ("*"), depending on the trust model. Each nested scope can only grant a subset of what its parent has.

Design

Permission model

Permissions are capabilities granted to a scope. A child scope cannot exceed its parent's permissions, it can only narrow them.

outermost: grant("*")              → everything allowed
  child:   grant_tcp("*.corp", 0)  → only TCP to *.corp hosts
    inner:  grant_tcp("db.corp", 0) → only TCP to db.corp

Aether implementation

The grant list and the block that enforces it come from std.sandbox:

  • sandbox.new(name) { grant_… } builds a grant list. The trailing block is a builder: each grant_* call inside it adds one grant.
  • sandbox.enforce(perms) { … } runs a block with those grants in force. Every sandbox-checked call inside it (and in anything it calls) must match a grant; nested enforce blocks intersect.
  • sandbox.free(perms) releases the list.

A Unix-domain socket is a file, and connecting to one takes write permission on it in the kernel too: tcp.connect_unix(path) and a std.http.client request with set_unix_socket(req, path) check fs_write on the path (resolved like any fs path), and tcp.listen_unix(path) checks tcp_listen and fs_write. So grant_fs_write("/var/run/*") also lets the block talk to every daemon socket there, docker.sock included: grant the socket's own path instead. The HTTP client asks on every request, so a connection pooled outside the block does not carry one made inside it. The LD_PRELOAD layer checks AF_INET and AF_INET6 connects only; libc makes AF_UNIX ones of its own (nscd, syslog).

The same grant list is what spawn_sandboxed(perms, prog, ...) hands a child process and what a host bridge takes as its perms argument (stunt.run_sandboxed(worker, code) here, tcl.run_sandboxed(worker, code) in aether-guest-languages).

The key insight

Trailing blocks { } are inlined, they CAN reach the enclosing scope. These are used for configuration (granting permissions).

The contained code is the block handed to sandbox.enforce. It can still name what is in scope (add seal except to stop that, see hide-and-seal.md), but every capability it exercises through std (files, environment, processes, sockets) is checked against the grants.

This maps directly to the container/contained boundary:

  • Container configures grants (trailing block, full access)
  • Contained runs with only what was granted (enforced block, restricted)

Working example

The contained code below calls ordinary os.getenv, fs.read, os.run_capture and os.exec. It does not know it is sandboxed; a refused call looks like a missing variable, an unreadable file or a failed command.

import std.sandbox
import std.os
import std.fs
import std.list

try_env(name: string) {
    if os.getenv(name) != null {
        println("  [ALLOW] env ${name}")
    } else {
        println("  [DENY]  env ${name}")
    }
}

try_read(path: string) {
    _content, err = fs.read(path)
    if err == "" {
        println("  [ALLOW] read ${path}")
    } else {
        println("  [DENY]  read ${path}")
    }
}

try_run(prog: string, arg: string) {
    argv = list.new()
    _a = list.add(argv, arg)
    _out, _status, err = os.run_capture(prog, argv, null)
    if err == "" {
        println("  [ALLOW] run ${prog} ${arg}")
    } else {
        println("  [DENY]  run ${prog} ${arg}")
    }
}

try_exec(cmd: string) {
    _out, err = os.exec(cmd)
    if err == "" {
        println("  [ALLOW] exec ${cmd}")
    } else {
        println("  [DENY]  exec ${cmd}")
    }
}

main() {
    // A worker that can read one config file and one variable
    worker = sandbox.new("db-worker") {
        grant_fs_read("/etc/passwd")
        grant_env("HOME")
    }

    // An untrusted plugin that may only run echo, with an argv: no shell
    // reads its arguments, so they cannot become a second command.
    plugin = sandbox.new("plugin") {
        grant_exec("echo")
    }

    println("=== db-worker ===")
    sandbox.enforce(worker) callback {
        try_read("/etc/passwd")
        try_read("/etc/hosts")
        try_env("HOME")
        try_env("PATH")
        try_exec("echo hi")
    }

    println("=== plugin ===")
    sandbox.enforce(plugin) callback {
        try_run("echo", "hi; uname")
        try_run("uname", "-a")
        try_exec("echo hi")
        try_env("HOME")
        try_read("/etc/passwd")
    }

    sandbox.free(worker)
    sandbox.free(plugin)
}

The plugin's echo gets hi; uname as one argument and prints it; no shell reads it. os.exec("echo hi") is refused because a command string runs through the shell, which the plugin is not granted.

What a command-string grant allows

os.system and os.exec hand their command string to the shell (/bin/sh -c, or on Windows the program COMSPEC names, cmd.exe), and the shell runs all of it. An exec grant is matched against the string as a whole, so grant_exec("echo *") matches "echo hi; rm -rf ~" and "echo $(id)" as well as "echo hi". For that reason a command string needs two exec grants: its own and the shell's, grant_shell(). The pair allows anything the shell can be told to run, so give it only to code you would let run any command. The LD_PRELOAD library applies the same rule to system() and popen().

A file with no #! line is a script too. os.run and its siblings, and os.execv, run one through /bin/sh, as execvp does, and the shell runs whatever the file holds, so it needs grant_shell() as well as the file's own grant. Without it the start fails with "permission denied" (#3755; #3762 for os.execv, which used libc's execvp and so took the shell by itself). A script that names its interpreter on a #! line needs no shell grant, since the kernel starts the interpreter itself. The LD_PRELOAD library asks the same of execvp and execlp.

// Untrusted code: name the program and pass an argv. No shell runs.
grant_exec("echo")              // os.run_capture("echo", argv, null)

// Trusted code that needs the shell: both grants, and the shell can run
// anything after "echo ".
grant_exec("echo *")            // os.exec("echo hi")

How containment works

Container sees contained

The sandbox.new("db-worker") { grant_… } block runs in the parent scope. The parent configures exactly what the worker can do, and has full visibility into the permissions it grants.

Contained cannot reach container

The block handed to sandbox.enforce(worker) { … } runs with the worker's grants in force: sandbox.enforce pushes the grant list as a level of the calling thread's, runs the block, then pops it. Every capability the block exercises through std (fs.read, os.getenv, os.exec, tcp.connect, …) is checked, and so is everything those functions call, however deep. Names are a separate matter: the block can still mention variables in scope. Add seal except (see hide-and-seal.md) when the block should not see them either.

Nesting rules

Sandboxes nest, and each level can only narrow permissions:

outer = sandbox.new("outer") {
    grant_tcp("*", 0)           // any TCP
    grant_fs_read("*")       // any file read
}

inner = sandbox.new("inner") {
    grant_tcp("db.corp", 0)     // narrowed to one host
    grant_env("HOME")        // outer has no env grant, so this adds nothing
}

sandbox.enforce(outer) callback {
    sandbox.enforce(inner) callback {
        // TCP to db.corp only; no file reads (inner did not grant them);
        // no HOME (outer did not grant it)
    }
}

The check consults every level in force on the thread and allows an operation only when each of them does, so the inner block gets the intersection of the two. An inner grant list cannot widen what an outer one refused.

Threads, libraries and panics

The levels belong to the thread that entered them, and are kept by the runtime (#2955):

CaseWhat holds
two threads, each in its own blockeach is checked against its own levels only; one leaving its block changes nothing for the other
a message sent from a blockhandled with no grants: an actor is not the block. That holds when the send steps an idle receiver of the same core inline, on the block's own thread: the step puts the block's levels aside and the block has them again when the send returns (#3393)
a library's export called from inside a block on the same thread (through a host service, say), one runtimeheld to the block's grants; its own enforce only narrows them, and when it ends the block is checked as before
the same, with libraries built without --shared-runtime (on every platform since #3481; a library linked before it, without -Bsymbolic, binds to the program's runtime on Linux and FreeBSD)each library has a copy of the runtime of its own, which cannot read another copy's grants: the inner library's checked operations are refused, and the first refusal prints a message naming --shared-runtime. Every copy finds the others by the record it carries in its image (a PE section, an ELF note, a Mach-O section), in load order, the program first: libraries a host loads, RTLD_LOCAL ones included, and a program with the libraries it loads, whenever it loads them and though its executable exports nothing (Windows, or Linux without -rdynamic, #3445: its copy went unfound, and the library's code inside its deny-all block was allowed everything)
a host bridge (stunt.run_sandboxed(perms, code), and the language bridges of aether-guest-languages)pushes perms as a level of the thread, so inside an enforce the guest gets the intersection
a panic out of a block, caught anywhere (a try in any code, an actor's barrier)the levels pushed inside the catching frame end with it, so the catch is held only to the blocks still around it
more than 64 levels on one thread (blocks, trusted calls, bridge calls)the 65th is refused with a panic before its block runs

sandbox_install() and sandbox_uninstall(), which a hand-written sandbox_push / sandbox_pop pair used to need, do nothing now: the push is all it takes. Aether code that needs the push and the pop apart (a level that is not one block) calls sandbox.enter(perms) and sandbox.leave() (std/sandbox/README.md, "enter and leave"): the list is lent rather than frozen, and the caller pairs them. A C host pushes and pops with aether_sandbox_push and aether_sandbox_pop (runtime/aether_sandbox.h).

A level cannot be widened from inside, either. enforce freezes the grant list when the block starts and checks against its own copy, which nothing else can reach, and the block's parameter is null rather than the list. So code inside the block that has been handed the list (plugin(worker)) and calls sandbox.grant_env(worker, ...) changes the caller's list for the next enforce, not the running one.

The * wildcard

grant_all() adds the wildcard category and pattern ("*", "*"), which matches every check. Within a category, a pattern of "*" matches any resource (grant_tcp("*", 0) is any host on any port), "/etc/*" a prefix, and "*.example.com" a suffix.

Listing, globbing or walking a directory reads the directory itself, so it needs a grant that matches the directory's path: grant_fs_read("/data/*") covers what is under /data, and grant_fs_read("/data") lets it be listed.

Every std call that touches the file system is checked the same way, by what it reveals or changes, on the path as it resolves:

  • fs_read: anything that reads a file or tells what is at a path. Opening for reading, fs.read/read_binary/copy (the source), std.io's read_file, file_info, fd_open_read and file_exists, and the metadata calls (fs.exists, dir_exists, file_stat, size, mtime, is_symlink, is_socket, readlink, realpath, statvfs), which are refused as reads: a stat tells whether something is there, which is what a grant list hides. A refused metadata call reads as absent (0) or as an error. A listing is a read of the directory listed: fs.list_dir(d) needs a grant matching d itself ("/data" or "/data*"; "/data/*" covers what is in it, not the directory). fs.glob checks the directory it starts from, refusing the glob when that is refused, reports only the paths the caller may read, and a ** glob enters only the directories it may read; fs.walk checks its root and each directory before entering it. The mount table is checked as /proc/self/mountinfo on every platform, so one grant serves everywhere.
  • fs_write: anything that creates, changes or removes. Opening for writing, std.io's write_file, append_file, delete_file and fd_open_write, fs.write*, unlink, chmod, create_dir, create_dir_with_mode, delete_dir, make_temp_* (the directory), symlink (the link), log.init's file, an HTTP server's access log, and each directory mkdir_p actually makes (one already there is walked through unchecked).
  • Both ends of a two-path call. copy reads its source and writes its destination; rename and move read and write their source (what is moved becomes readable where it lands) and write their destination; hard_link writes the new name and reads and writes the target, since the link is a second name for it. A symbolic link's target is not checked when it is made: every later use of the link is checked where it leads.
  • os.chdir and a child's working directory (os.run_stdio's cwd) are checked under "fs" (grant_fs); dl.open under "native" (grant_native); http.serve_file/serve_static and an HTTP server's TLS key and certificate files under fs_read, a refused file being served as 403 whether or not it exists.

Nested sandboxes are intersected, an inner sandbox cannot escalate beyond what the outer sandbox grants.

What each mode holds, and what it does not

The sandbox runs in three modes. They share one grant list, one matcher and one path resolution, and differ in who makes the check and whether the kernel stands behind it.

In-process enforce (sandbox.enforce, a host bridge's run_sandboxed). The checks are std's own, made by the calling thread against its levels.

  • Holds: every std call in the table above, checked where its path leads, and made on what was checked (#3751), so a directory swapped for a symlink or a junction by another thread or process between the check and the call is not followed out of the grant:
    • On POSIX the call is made on the resolution following no symlink: an open with openat2 and RESOLVE_NO_SYMLINKS on Linux where the kernel has it, otherwise one directory at a time from / with O_NOFOLLOW; a call on a name (unlink, rmdir, rename, mkdir, symlink, link, chmod, a lookup) with its *at variant from the directory opened that way. fs.write_atomic makes its temporary and renames it from that directory; fs.make_temp_file and fs.make_temp_dir make their name in the directory that was checked; fs.walk descends with openat from each directory; the lookups (fs.exists, fs.stat, fs.size, fs.mtime, fs.is_dir, fs.is_symlink, fs.readlink, fs.realpath, fs.statvfs) are fstatat (or readlinkat, or fstatvfs of a walked descriptor) from the anchor; fs.watch watches the walked descriptor through /proc/self/fd/N (inotify) or the descriptor itself (kqueue); std.tar sets times with utimensat from the anchor. A name spelt with a trailing slash is a directory, as the kernel takes it (see the standalone preload below). On WASI the walk starts from the preopened directory that holds the path, which wasi-libc reaches only through it.
    • On Windows what a call acts on, or the directory it acts in, is opened without changing it and the final path of the handle is checked (GetFinalPathNameByHandleW) before anything happens: an open for writing never truncates or creates by name (no CREATE_ALWAYS or TRUNCATE_EXISTING); the file is emptied with SetEndOfFile once verified, and a file the call created and then refused is deleted through its handle. Only an open that may create asks for DELETE, and once verified its handle is reopened without it (ReOpenFile), so the file is shared as fopen shares it; where DELETE cannot be had the new file is made by NtCreateFile in the verified directory instead. Unlink, rmdir and remove set the disposition of a handle opened with DELETE and FILE_FLAG_OPEN_REPARSE_POINT; rename and a hard link go through NtSetInformationFile with the verified destination directory as RootDirectory; mkdir, mkdir -p, fs.write_atomic's temporary and the temporary files are made by NtCreateFile relative to a verified directory; fs.copy copies between two checked handles; a lookup, fs.readlink and fs.realpath verify the handle they read; fs.watch reads changes from a verified directory handle (ReadDirectoryChangesW); fs.chmod changes the DACL (SetSecurityInfo) and the read-only attribute (SetFileInformationByHandle) through a verified handle, and std.tar sets times through one (SetFileTime); fs.list_dir, fs.walk and fs.glob list a verified directory handle (NtQueryDirectoryFile, a glob's last part matched by the file system as FindFirstFileA matches it), each subdirectory opened relative to its parent with no link followed, as the POSIX walk enters no symlink. The name a call makes is the one a Win32 call acts on: the whole path goes through GetFullPathNameW first, so a trailing dot or space is dropped and a device name is the device (\\.\NUL, its own resource, covered by a grant that names it or by grant_all, as /dev/null is on POSIX). A symlink is made by name (CreateSymbolicLinkW has no handle form), then opened and verified, and removed again if a swap sent it elsewhere.
  • Calls on a name check that name (its directory resolved, the name kept), not where a symlink there leads: removing a symlink in a granted directory that points out is allowed and leaves its target alone, and removing or renaming one outside the grant that points in is refused. A hard link needs fs_write on the new name, and the new name may not reach the file more than the old one may (fs_read and fs_write on the target for whichever the new name has).
  • fs.lock_open needs fs_write, as it always has; inside an enforce block its descriptor reads as well only where fs_read is granted too (the lock itself, flock or LockFileEx, takes a write-only one).
  • Does not hold: code that does not go through std (an extern, inline assembly, a library's own calls), other threads (each thread has its own levels), and a few windows that remain by the platform's design. On Windows a symlink exists for a moment, by name, before it is verified and removed, and so does a file an open creates through a junction swapped in after the check: it is made where the junction leads, outside the grant, then found by the verification and deleted through its handle before anything is written to it (where DELETE cannot be had it is made in the verified directory, never outside); a hard link is refused before anything changes. On a POSIX system whose *at calls re-resolve by name instead of from the descriptor (Cygwin and MSYS2 emulate them so), the walk holds nothing more than a check by name. Without /proc on Linux, fs.watch watches by name and compares the file it reaches with the one it opened. There is no kernel backstop: the levels are entered and left, and Landlock cannot be lifted once applied, so an in-process enforce block cannot ask the kernel to hold it.

Standalone preload (LD_PRELOAD=libaether_sandbox.so with a grant file, the shared memory or the descriptor spawn_sandboxed hands over). The checks are the library's, at libc's entry points, for every thread of the process.

  • Holds: every libc call that opens, lists, creates, removes or changes a file by path (open and its large-file and _FORTIFY_SOURCE variants, openat, creat, fopen, freopen, opendir, scandir, scandirat, glob, nftw, ftw, fts, unlink, unlinkat, remove, rmdir, mkdir, mkdirat, mknod, mkfifo, rename, renameat, renameat2, symlink, link, chmod, lchmod, fchmodat, chown, lchown, fchownat, truncate, the times, the extended attributes, mkstemp and its kin, mkdtemp, tmpfile, open_by_handle_at, mount, posix_spawn_file_actions_addopen; on FreeBSD also scandir_b, scandirat_b, mkostempsat, the file flags, the extended attributes and ACLs set by path, funlinkat, revoke, undelete, nmount, unmount, exect and libc's exported _open and _openat), each made in the same three steps as in-process: resolved (relative to its directory descriptor for an *at call, read from /proc/self/fd or F_KINFO; it was the working directory), checked, and made on the resolution following no symlink. A chmod that glibc before 2.32 cannot make without following goes through /proc/self/fd/N of the name opened O_PATH|O_NOFOLLOW, or through a descriptor opened for it. A freopen with a path reopens the stream through /proc/self/fd/N of the file the walk opened, or on the BSDs puts that descriptor in the stream's place (dup2) and reopens it with no name. A name spelt with a trailing slash ("name/") is a directory, as the kernel takes it: an unlink of one never removes anything (ENOTDIR, or EISDIR for a directory), an open that would create is EISDIR, a rename moves a directory only, and a new symlink, hard link or node is not made (EEXIST or ENOENT); an open of one follows the name and needs a directory there. A hard link whose source is a descriptor (linkat with AT_EMPTY_PATH, or /proc/self/fd/N with AT_SYMLINK_FOLLOW, the ways an O_TMPFILE file gets its name) needs fs_write on the new name, which may not reach the file more than the path the descriptor is open on may, and is made with the caller's own spelling of the source. lsetxattr and lremovexattr open the name O_PATH|O_NOFOLLOW and set through /proc/self/fd/N. mount checks fs_write on the mount point and, for a bind or a move, fs_read on the source (and fs_write unless the bind is read-only), and passes both as resolved; FreeBSD's nmount does the same for a nullfs or unionfs source ("target", "from"), and its mount(2) refuses those. unshare and clone with a CLONE_NEW* flag, clone3 with one, and setns need the native grant their system call needs (syscall:unshare, syscall:setns): a new user and mount namespace would let a bind mount show any directory where a grant allows. The process starts (execve and the rest of the family, posix_spawn, fork, system, popen), dlopen and dlmopen, connect, bind, listen, accept, getenv, raw syscall(), and executable memory. A test lists every path call of glibc, musl and FreeBSD's libc and fails on one that is neither wrapped nor named as a lookup (tests/integration/sandbox_preload_fs_coverage).
  • Lookups are not wrapped: stat and its kin, access, readlink, realpath, getxattr, statfs, pathconf, chdir, FreeBSD's ACL and extended attribute reads. They say that a name exists and what it is, never what it holds, and libc and the runtime make them for their own needs (a PATH search, the resolution above). mkdir of a name that exists answers EEXIST without a grant, as a lookup would, so mkdir -p works through the directories above a grant.
  • A permanent policy is held by the kernel too. A grant file (or the shared memory or descriptor) with the line policy:permanent says the policy is the process's for its whole life. The constructor then applies Landlock to the whole process from its grants, before main: fs_read, fs_write, fs and exec grants become Landlock rules as they do for a spawned child, tcp grants with a port become connect rules on Landlock ABI 4 and up (with no tcp grant, connect is refused; a tcp grant with no port or a tcp_listen grant leaves that right to the wrappers), and the floor a running program needs is added (the loader's cache and its C library's directory, the locale archive, /dev/null, /dev/urandom), with the preload library, the grant file and the shared memory the grants came from, which a program it starts reads to keep the policy. A program an exec grant names gets what the kernel needs to start it, its ELF interpreter and the libraries beside it, or a #! script's interpreter, and with any exec grant this program's own interpreter is executable; with a tcp grant that names a host, the files the C library reads to resolve it (/etc/resolv.conf, /etc/hosts, /etc/nsswitch.conf, /etc/host.conf, /etc/gai.conf, /etc/localtime) are readable. An fs grant becomes a rule only on what the libc check would match: a path spelt through a symlink, and an entry of "/dir/name*" that is a symlink, get none, so no rule reaches the tree a symlink points at. The log is opened first, and the restriction sets PR_SET_NO_NEW_PRIVS, so a set-user-ID program the process starts no longer gains its owner's rights. Without the line nothing changes. On a kernel without Landlock, or with a grant Landlock cannot express (a suffix pattern such as *.log), the policy holds at libc only, and the log says so (AETHER_SANDBOX: landlock: ...).
  • Does not hold, without policy:permanent or without Landlock: anything that does not call libc's exported functions (a static binary, a raw syscall instruction, io_uring), libc's calls to itself (glibc's fopen opens on its internal open, which is why fopen has a wrapper of its own), and a process that unsets LD_PRELOAD before an exec the policy allowed. On Linux with /proc not mounted, an *at call from a directory descriptor is refused (the descriptor's path cannot be read) and a freopen with a path reopens by the resolved name. FreeBSD's ACL, extended attribute and revoke calls have no form relative to a directory and are made by the resolved name.

Spawned child (spawn_sandboxed, sandbox.spawn_socket). The preload, as above, inside the child, and on Linux the kernel behind it: Landlock holds the child's file access to the grants (read and write by path, inherited by everything it starts, a static binary included), and a seccomp filter holds process creation, ptrace and the other raw calls listed below. On FreeBSD an Aether child also enters Capsicum. With a permanent policy the standalone preload's process has the Landlock half of this; the seccomp filter stays the spawn's.

Choose by what runs: trusted Aether code limiting itself, in-process; cooperative native code (a plugin, an interpreter) in this process, the preload, with policy:permanent where nothing will lift the policy; code that may try to escape, a spawned child on Linux or FreeBSD.

Per-function effect tags

The sandbox and --with=fs,net,os gate the whole program. Effect tags add a finer, per-function capability axis, checked statically at compile time (zero runtime cost):

@pure
parse_config(text: string) -> Config { ... }   // must touch no fs/net/os

@no_fs
classify(req: Request) -> int { ... }            // must touch no filesystem
  • @pure forbids all of fs/net/os; @no_fs / @no_net / @no_os forbid one capability each (stackable: @no_fs @no_net f() {}).
  • A whole-program pass walks the call graph from each tagged function. If it reaches a capability-gated stdlib call, file.*/dir.*/path.* (fs), tcp.*/http.* (net), os.* (os), directly or through another function, the compile fails with the offending call path named.
  • Composes with --with=: that switch says the program may use fs; an effect tag says this function must not. The two axes are independent.
  • A raw extern call is unclassifiable (the compiler can't know a foreign symbol's effects), so it is not flagged, the same boundary the --with= import gate has.

Path resolution before fs match

An fs resource is matched where it leads, not as it is spelt, by both layers: the in-process checks in std and the LD_PRELOAD library share one resolver (runtime/aether_sandbox_path.h). It walks the path a component at a time, as the kernel does: . is dropped, .. goes to the parent of what is resolved so far, and a component that exists is resolved with realpath(3), so a symlink is followed to where it points. A component that does not exist yet (a file about to be created, directories mkdir -p will make) is kept as written, and a .. after it removes it again. So a grant for /box/* is not left through /box/../etc/shadow, mkdir -p /box/../x/y, a symlink in /box that points out, /box/link/../x when link points out, or a dangling symlink in /box whose target is outside.

Resolving .. as text first would be wrong: with link pointing at /elsewhere/dir, /box/link/../x opens /elsewhere/x.

A path that cannot be resolved (a dangling symlink, a loop, a directory that cannot be searched) is refused, not matched as written.

An fs grant's pattern is resolved the same way when it is made (grant_fs_read("/var/x/*") covers /private/var/x/... on macOS, and a grant named through a symlink covers where the symlink leads); * and suffix patterns such as *.log are kept as written.

On Windows . and .. are resolved by the text first, as Windows itself resolves them before the file system sees a path (GetFullPathNameW). The deepest part of the result that exists is then opened and GetFinalPathNameByHandleW says where it really is, every junction and symbolic link on the way followed; the names below it that do not exist yet are kept as written. So a junction in a granted directory that points outside it is refused, as a symlink is on POSIX, and a name that exists but cannot be followed (a link whose target is gone) is refused rather than matched as written. Until #3763 the path was only normalised with _fullpath, which follows nothing, and a junction in a granted C:\box reached anything it pointed at.

Non-fs categories (tcp, env, exec) carry no path semantics; their resources are matched verbatim.

Scope boundaries

The sandbox mediates stdlib I/O only. These are the places its enforcement line sits, and where it deliberately stops.

Extern calls bypass the sandbox

Aether's extern keyword lets code call raw C functions directly. If contained code declares:

extern fopen(path: string, mode: string) -> ptr

It can call fopen directly, bypassing file_open and its sandbox check entirely. The sandbox enforces stdlib calls, not raw C.

Today: under --emit=lib it is enforced at compile time: a library built without --with=extern may not declare its own externs (see docs/emit-lib.md, "Capability-empty default"), so a capability-empty library cannot name fopen or system itself. In an executable, extern calls inside sandboxed closures still compile and run without restriction; the check below is the remaining step.

Impact: the sandbox is effective when you control compilation and don't put extern declarations in contained code. It's the same trust model as Docker, you trust the container runtime (Aether's stdlib), but the contained code must use the provided APIs.

Proposed fix: compiler-enforced extern check

The compiler should reject extern function calls inside closures passed to run_sandboxed. Implementation:

  1. Track whether codegen is inside a sandboxed closure (similar to in_trailing_block)
  2. When generating an AST_FUNCTION_CALL that resolves to an AST_EXTERN_FUNCTION, check if we're in a sandboxed context
  3. Emit a compile error: "extern calls not permitted in sandboxed code"

This is a typechecker/codegen change, not a runtime change. It would make the sandbox inescapable at compile time, analogous to Java's ClassLoader preventing contained code from seeing restricted classes.

The key insight: extern restriction is a compilation concern. The sandbox grants (tcp, fs, exec, env) are a runtime concern. Both are needed for complete containment:

Compile time: reject extern in sandboxed closures
Runtime:      check grants before stdlib operations

This matches Java's two-layer model: ClassLoader isolation (compile/link time) + SecurityManager checks (runtime). Java removed the runtime layer (SecurityManager) but kept the compile/link layer (module system). Aether should have both.

Other boundaries

  • No deny grants. The model is deny-by-default, grant what's needed. There is no way to grant broadly then carve exceptions. This is intentional for the initial release.
  • Ports are checked. grant_tcp("db.internal", 5432) allows that port only; 0 allows any port. The check names the resource host:port ([v6]:port for IPv6), in std.net and in the LD_PRELOAD layer's connect() alike. Grant an IPv6 host as grant_tcp("::1", 8443) (stored as [::1]:8443). A grant for one family never admits the other: 127.0.0.1 does not cover ::1. An IPv4-mapped peer (::ffff:127.0.0.1, how a dual-stack socket reaches an IPv4 host) is the IPv4 host, and matches its grant.
  • Unreadable grant sources deny everything. If the preload layer is configured with a grant source (AETHER_SANDBOX_SHM or AETHER_SANDBOX_GRANTS) that cannot be read, or is larger than the size limit, the sandbox stays active with zero grants rather than running unrestricted.
  • An empty grant list starts the child with nothing allowed. spawn_sandboxed with no grants runs a compute-only worker: it can use the pipes it was given, but no files, exec or network. Malformed lists (odd length, a : in a category, CR or LF in a category or pattern) and lists over the transport size limit are refused with -1 and the message "invalid grant list" or "grant list too large".
  • Every libc way of starting a program is held to the same two rules. A new process needs what fork needs (under a grant file, the fork grant), and the program run needs its exec grant. The preload holds these at execve, fork and clone3, and also at each call libc implements on its own internal execve, clone or vfork, which the execve and fork wrappers never see:
    • the rest of the exec family (execv, execvp, execvpe, execl, execlp, execle, fexecve, execveat, FreeBSD's execvP);
    • posix_spawn, posix_spawnp, glibc's pidfd_spawn/pidfd_spawnp and _Fork;
    • system, popen and wordexp's command substitution, which run /bin/sh and so need an exec grant for it.

The p forms search PATH in the preload, so the grant is checked against the file that runs. A file with no #! line that execvp runs through /bin/sh needs the shell's grant as well as its own. tests/integration/sandbox_spawn_family holds the whole grid on Linux and FreeBSD. Before this, a process under a grant file with no exec grant could still run any program through any of them; so could a guest language's os.execute in-process.

  • A child's environment keeps the sandbox controls. execve and the spawn calls re-add LD_PRELOAD and the AETHER_SANDBOX_* / AETHER_CAPSICUM entries the preload captured at startup, so the child stays contained and edits to the live environment do not change them. system and popen run the shell with the live environment, which cannot be rebuilt there: under a grant file they are refused when it no longer carries exactly the controls the process started with.
  • Application-level only. See "Cross-process containment" below for extending enforcement to child processes.

Audit trail

Denial logging above covers the cross-process (LD_PRELOAD) layer. The in-process layer, the stdlib grant checks an in-program sandbox { } block drives, and the checks embedded/hosted plugins go through, has its own audit trail, recording every permission decision, allowed as well as denied.

Live sink

Set AETHER_SANDBOX_AUDIT same shape as AETHER_SANDBOX_LOG:

Queryable log, std.audit

The last 256 checks are also held in an in-memory ring buffer that the program can read back through the std.audit module:

import std.audit

// ... run sandboxed work ...

n = audit.count()
for (i = 0; i < n; i = i + 1) {
    cat, res, allowed = audit.entry(i)   // allowed: 1 = passed, 0 = denied
    // ...
}
println("${audit.denied_count()} denials of ${n} checks")
audit.clear()                            // scope the next query

This is the programmatic face of the audit trail: counting denials, asserting an expected access pattern in a test, building a "why was this blocked" report. Worked example: examples/05-containment/03-audit.ae.

The in-process layer (module boundary, scope boundary, and the stdlib grant checks) is pure C and works on every platform regardless.

A sandboxed child with a socket: sandbox.spawn_socket

ch, pid, err = sandbox.spawn_socket(guest, "python3", argv, env)

os.run_socket's channel (the child's fd 3, AETHER_IPC_FD=3, AETHER_IPC_KIND=socket) with spawn_sandboxed's containment, held to the grant list: the preload library, and the kernel layer below ("Kernel layer"). argv is a std.list of the arguments after the program and env the child's whole environment as "KEY=VALUE" (null for this process's); the sandbox adds its own variables. It returns at once with the parent's end of the socket and the child's pid; reap the child with os.wait_pid and close the socket.

It fails closed. Where the child cannot be contained (macOS, Windows, Android, and FreeBSD until it has a kernel layer for a foreign program), and on Linux when the preload library cannot be found or the kernel layer cannot be set up as asked, it returns (-1, -1, reason) and starts nothing. A host that wants a child with no sandbox at all asks for one by name, sandbox.spawn_socket_uncontained(perms, ...): the same signature (the grants are ignored), so the two differ by one word and the uncontained one is easy to find in review.

The grants reach the child's preload on a sealed memfd it inherits (AETHER_SANDBOX_GRANTS_FD), not on a named shared-memory object: spawn_sandboxed waits for its child and then removes the object, and spawn_socket does not wait. The memfd has no name to remove, its seals stop the child changing it, and a program the child is granted to exec reads the same grants from it.

For a guest that runs scripts for the host (an engine compiled into a worker, or an interpreter), std.guest is the conversation on top of this socket: it spawns with spawn_socket, mounts the functions the script may call, answers each call (a file as an open descriptor), and bounds every exchange with a deadline, then a CANCEL, then a kill. std.guest.child is an Aether worker's side, and enters sandbox.enforce with no grants before the script's first step. A script may also leave functions behind for the host to call later (READY, then INVOKE and RETURN or RAISE, strictly alternating, each exchange under the same deadline); an invoked function reaches only what the host mounted, so being callable gives the child no new capability. Its README (std/guest/README.md) has the protocol, and docs/design/guest-host-calls-guest.md the design of the host-calls-guest direction.

Starting a foreign interpreter: grant_runtime

Under the kernel layer a child reads nothing it is not granted, and an interpreter has to read its own library before it runs a line. Two kinds of guest, two answers (aether#3503):

  • An Aether worker locks itself down after it starts: it calls sandbox.enforce before its first step, so it needs no start-up grants and no platform paths (the cap_enter shape).
  • A foreign interpreter cannot, so the host grants what it needs to start with a preset:
guest = sandbox.new("python-guest") {
    grant_runtime("python3")           // its stdlib, lib-dynload, site-packages, libpython
    grant_fs_read("python/guest.py")   // the script is the host's to grant
}
ch, pid, err = sandbox.spawn_socket(guest, "python3", argv, null)

grant_runtime asks the interpreter, in the unsandboxed host, when the grant list is built: python3 -I -c ... prints the directories on its sys.path (-I leaves out PYTHONPATH, the user's site-packages and the current directory) and libpython's file, and each becomes a read grant (dir/*, a file, or libpython3.X.so*). The interpreter knows where this machine's install keeps them, a distribution's /usr/lib/python3.X, a Homebrew or pyenv prefix, /usr/local; a table of paths would guess, per platform, and go stale. The table in std/sandbox/module.ae says only which interpreters can be asked and how (python3, python today). A name it does not know, or an interpreter that cannot be asked (not on PATH, or exiting non-zero), grants nothing and returns the reason, "" otherwise: check it where the list is built (why = grant_runtime("python3") in the block) to report that rather than the child's failure to start. A list without the runtime's library fails closed. (Through 0.926.0 it panicked, which took a host process down with it.) It grants no exec (the interpreter is the program the spawn runs) and not the guest's script.

Where spawn_sandboxed finds the preload library

The child starts with libaether_sandbox.so in LD_PRELOAD, so the parent has to find it wherever the parent program runs: in ae run's build cache, in a directory ae build -o wrote to, or installed beside other programs (#3177). spawn_sandboxed, the contrib process host (contrib/host/aether) and the go and java bridges of aether-guest-languages look in this order:

  1. AETHER_SANDBOX_PRELOAD, the library's own path, when it is set;
  2. beside the running program, where a deployment can ship it;
  3. under AETHER_HOME, which ae sets for every program it runs: lib/aether/ (what install.sh and make install install), lib/ (a release archive's layout), then build/ (a source tree, where make builds it);
  4. the same three under the program's directory's parent: a program installed in <prefix>/bin, or one in a source tree's directory.

When none has it, the call says where it looked and returns -1 without starting the child.

Windows is out by construction, not by backlog. The interception model is LD_PRELOAD + dlsym(RTLD_NEXT, ...); Windows has no equivalent, so this is not a port waiting to be written. Two consequences worth stating plainly:

  • Running Windows binaries under Wine does not exercise containment. Preloading into the wine process intercepts wine's own libc calls, not the guest program's, so a green run there would be actively misleading. Should a Wine-based test lane ever land, the sandbox suites must stay excluded from it; tests/ae_sweep_prune_wine.txt records that.
  • README's "enforced from compile time down to libc" is therefore a Linux/FreeBSD claim for the libc tier. On Windows the compile-time (--emit=lib capability gating) and scope (hide / seal except) layers apply; the runtime tier does not.

Security review checklist

Before signing off an Aether sandboxed deployment, verify:

1. LD_PRELOAD is active

The sandbox preload library must be in the LD_PRELOAD chain. Without it, there is no interception, all libc calls pass through unfiltered.

# Verify for spawned processes:
grep LD_PRELOAD /proc/<pid>/environ

For spawn_sandboxed() this is automatic. For manual deployments, the launch script must set LD_PRELOAD=libaether_sandbox.so.

2. No wildcard exec grants

grant_exec("*") allows executing any binary, including statically linked ones that bypass LD_PRELOAD. Exec grants should be specific:

// Bad:
grant_exec("*")

// Good:
grant_exec("python3")

A command-string grant such as grant_exec("echo *") allows nothing without grant_shell(), and with it the shell runs whatever follows the matched prefix (see "What a command-string grant allows" above). Name the program instead and spawn it with an argv.

3. No statically linked binaries in granted paths

A statically linked binary doesn't use libc, it talks to the kernel directly, bypassing all LD_PRELOAD interception. Verify no static binaries exist in any path accessible to the sandbox:

# Check for statically linked binaries in /usr/bin
find /usr/bin -type f -exec file {} \; | grep "statically linked"
# Should return nothing on stock Debian/Ubuntu

Go binaries are the primary risk, they're often statically linked. Don't grant fs_read to directories containing Go binaries unless the sandbox needs them.

4. Native loading is restricted

grant_native("*") allows dlopen of any shared library, including libc.so.6 directly. This enables ctypes/Fiddle/DynaLoader escape. Don't grant it unless necessary. Without it:

  • Python ctypes.CDLL("libc.so.6") is blocked, and so is ctypes.CDLL("/usr/lib/x86_64-linux-gnu/libc.so.6"): the preload matches libc and the dynamic loader (glibc's libc.so.6, musl's libc.musl-*.so.1, ld-linux*, ld-musl-*, FreeBSD's libc.so.7 and ld-elf.so.1) by the basename of the name, by the basename of where a path leads (symlinks, .., /lib or /usr/lib), and by the handle the loader returns (a name found on LD_LIBRARY_PATH)
  • Perl DynaLoader::dl_load_file("libc.so.6") is blocked
  • Ruby Fiddle.dlopen("libc.so.6") loads but calls are still intercepted
  • Lua has no FFI, not a vector

That is the preload layer. A guest that finds libc's syscall some other way (its address read from libc's symbol table in memory, say) is past it; on Linux, Landlock under sandbox.spawn_socket is what refuses the open that follows.

5. Grant list follows least privilege

Review grants like you'd review Docker capabilities:

// Each grant should be justified
worker = sandbox.new("worker") {
    grant_env("DATABASE_URL")       // needs DB connection string
    grant_fs_read("/app/config/*")  // needs config files
    grant_tcp("db.internal", 0)        // talks to database
    // Nothing else, deny by default
}

No grant_all() in production. No broad grant_fs_read("*"). No grant_env("*").

6. Log file is monitored

aether-sandbox.log records all denied operations. In production:

  • Ship it to your log aggregator
  • Alert on unexpected denials (may indicate misconfiguration or attack)
  • Periodically review for grants that can be tightened

7. Sandbox code is auditable

The sandbox policy is Aether source code, readable, diffable, reviewable in a PR. Unlike Docker's layered Dockerfile + compose + k8s manifests, the entire policy is in one place:

# The security review is: read this file
cat sandbox-config.ae

Raw syscall()

libc's syscall() is interposed so it cannot be used to go round this library: a raw call skips the argument checks the wrappers make (the file system calls below, connect), and some calls have no libc wrapper here at all (sendto, kill, ptrace). fs.write_atomic under the preload

fs.write_atomic(path, data) writes a new file beside path, <path>.tmp.<pid>.<n>, and renames it over path. A grant on path covers it in both layers: std checks path, and for the one open that creates the temporary it tells the preload which file the temporary stands for (aether_sandbox_stage in runtime/aether_sandbox.h), so the preload checks path too, under an in-process level and a grant file alike. It does that only for an open that creates a new file (O_CREAT|O_EXCL) named exactly <path>.tmp.<this pid>.<digits> on the thread that staged it; any other open is checked under its own name, so the stage cannot open an existing file or reach past that one sibling. The rename of the temporary over path, and its removal when the write fails, are staged the same way (#3751, which wraps rename, unlink and remove): checked as writes of path, for that one name only.

Kernel layer: Landlock

LD_PRELOAD sees only calls that go through libc. Python's ctypes, LuaJIT's FFI or Ruby's fiddle can reach libc's own syscall (or a static binary can issue the instruction), and open what the grants never allowed. On Linux both sandboxed spawns (spawn_sandboxed and sandbox.spawn_socket) therefore put the child under Landlock before it execs: Linux 5.13 and later, no root, no user namespace. Its rules come from the grants, so the kernel refuses such an openat itself (EACCES).

The ruleset is built in the parent, before the fork, and the child only applies it (PR_SET_NO_NEW_PRIVS, then landlock_restrict_self), which keeps the child to async-signal-safe calls. Its code is runtime/sandbox/aether_sandbox_kernel_linux.c.

How grants become rules. The ruleset handles every fs right of the kernel's ABI (REFER from ABI 2, TRUNCATE from ABI 3; IOCTL_DEV is not handled, so ioctls on already-open terminals keep working).

What the child may read to start. Under Landlock the child's own execve is checked too, and so are the opens the dynamic loader makes, which the preload never sees. The kernel layer adds, read-only:

  • the program (EXECUTE, READ_FILE), its ELF interpreter from PT_INTERP (EXECUTE, READ_FILE), and for a #! script its interpreter the same way; a file that is neither runs under /bin/sh, which gets the same;
  • the directory the ELF interpreter really lives in, READ_FILE only (no listing): the system library directory, /usr/lib/x86_64-linux-gnu on Debian and Ubuntu, /usr/lib on Arch and Fedora. Libraries elsewhere (/usr/local/lib, $ORIGIN) need a grant_fs_read;
  • /etc/ld.so.cache, /usr/lib/locale (glibc's locale archive) and /dev/urandom (READ_FILE); /dev/null (READ_FILE, WRITE_FILE);
  • libaether_sandbox.so, and spawn_sandboxed's shared-memory grant file (spawn_socket's grants are on an inherited memfd, which needs no rule).

On ABI 1 (Linux 5.13 to 5.18) REFER does not exist and the kernel refuses every rename or link across directories under a ruleset; that is Landlock's own rule.

A kernel without Landlock (older than 5.13, or with landlock left out of lsm=):

  • sandbox.spawn_socket fails closed: it returns an error naming the missing Landlock and starts nothing. A host that accepts the weaker containment says so in its grant list with grant_without_landlock(), and the child then runs with the preload and seccomp only;
  • spawn_sandboxed keeps working for the callers it had before Landlock, and prints a warning to stderr (once per process) that a raw syscall can now open what the grants do not allow.

Kernel-level fence for process creation, the clone3 gap, closed

The LD_PRELOAD layer cannot intercept syscalls that don't go through exported libc symbols. Two notable bypasses, both common:

  • glibc __vfork on x86_64 is an inline syscall instruction in libc's text. LD_PRELOAD never sees it, there's no symbol to interpose.
  • Any program calling syscall(SYS_clone3, …) (or issuing the raw syscall instruction directly).

Modern gcc on Linux uses both paths to spawn cc1/as/ld. So a purely libc-symbol-level fence on fork:* was a paper tiger against real toolchains.

spawn_sandboxed therefore installs a seccomp-bpf filter on the child side (post-fork, pre-exec) that refuses the child a new process however the call is made, when fork:* (grant_fork()) is not in the grant list: fork and vfork get EPERM, and so does a clone without CLONE_THREAD. A thread is no new process: it shares the address space, the filter and the preload, so a clone with CLONE_THREAD passes (#3178) and a child can run actors, threads in Python or a JVM. clone3 keeps its flags in a struct in memory, which a filter cannot read, so it gets ENOSYS, the answer of a kernel without clone3, and libc falls back to clone, whose flags the filter reads. This is true kernel-level enforcement, immune to call-site obfuscation. Requires Linux ≥ 3.5 (PR_SET_NO_NEW_PRIVS + PR_SET_SECCOMP). The filter covers x86_64, aarch64, riscv64 and loongarch64, and every ABI a process there can enter the kernel through: on x86_64 the i386 ABI (a static 32-bit binary, which LD_PRELOAD cannot reach either) and x32, on aarch64 32-bit ARM. Each is trapped with its own syscall numbers. Any other ABI kills the process, and on an architecture the filter does not cover spawn_sandboxed refuses to run the child (below) rather than fall back to the libc-level fence alone. The kernel fence is automatic: with fork:* (grant_fork()) granted the process-creation rules are left out, and the rest of the filter (below) stays. If the kernel doesn't support seccomp, the child aborts with exit(126) rather than silently running uncontained a spawn_sandboxed that asked for containment we can't deliver must not exec.

The program's own exec. The filter is installed before the child execs its program, and that one execve has to pass. Without grant_exec, the filter allows execve only when its first argument is the exact pointer the child passes (the resolved program, or /bin/sh for a file with no #! line), compared in all 64 bits; a compat ABI's execve is always refused. Once the program runs that pointer means nothing, and the preload's constructor, before any of the program's own code, installs a second filter that refuses every execve and execveat (the spawn sets AETHER_SANDBOX_NO_EXEC=1; a filter that cannot be installed stops the process with exit 126). Filters stack and the strictest answer wins, so the child cannot undo it. A static program, which the preload never enters, keeps the pointer check and Landlock, under which it can execute only its own file and its loader.

ABIs. The filter dispatches on seccomp_data.arch: the native ABI's numbers, on x86_64 also i386 (int 0x80) and x32 (the number with 0x40000000 set, masked off, plus x32's own numbers for execve, execveat, ptrace and process_vm_*), on aarch64 also 32-bit ARM. Any other ABI kills the process. On an architecture the filter does not cover, both spawns refuse to start the child. The numbers are literals, checked against the kernel headers zig ships for every architecture by tests/integration/sandbox_clone_fence, and every filter the builder can make is checked well formed by tests/integration/sandbox_spawn_socket.

os.spawn_tree_to inside a sandboxed child. Its supervisor is a fork of the program that called it, so it runs under the same preload and filter. It needs grant_fork() (without it the spawn fails with "fork failed", the filter's EPERM) and, on Linux, a read of /proc (grant_fs_read("/proc/*")), which is how it finds a descendant that left the program's group. The spawn probes that read first and fails with "cannot read /proc" when the sandbox refuses it, so a tree is never started that tree_kill could only half end. Its other calls (prctl for the subreaper, kill, waitpid) pass the filter. tests/integration/sandbox_spawn_tree runs the three cases.

Interception surface, what LD_PRELOAD sees and what it doesn't

Lesson from Google App Engine (2013): An intern broke out of App Engine's Java sandbox by exploiting a gap between what the bytecode rewriter (ASM) thought it serialized and what the JVM actually parsed. The architectural lesson: if the enforcement layer and the execution layer see different things, an attacker can exploit the difference.

For Aether, the equivalent gap is: we intercept specific libc functions, but the kernel offers many alternative paths to the same operations. What the contained code sees

To the contained code, a denied resource looks like it was never there: open("/etc/shadow") fails as if the file did not exist, and getenv("AWS_SECRET_KEY") returns null as if the variable were unset. The check is invisible; the contained code can't distinguish a denial from an absent resource.

Sandboxing bash scripts

Bash is a common choice for build steps, deployment scripts, and system orchestration. It can be sandboxed via spawn_sandboxed, but with an important caveat.

The model: Aether orchestrates, bash works

Aether is the guard. Bash is the tool. Each bash invocation gets specific grants for that step:

compile_sandbox = sandbox.new("compile") {
    grant_fs_read("src/*")
    grant_fs_write("build/*")
    grant_exec("/usr/bin/gcc")
    grant_exec("/usr/bin/bash")
}

deploy_sandbox = sandbox.new("deploy") {
    grant_fs_read("build/bin/*")
    grant_tcp("deploy.internal", 0)
    grant_exec("/usr/bin/bash")
    grant_exec("/usr/bin/scp")
    grant_env("DEPLOY_TOKEN")
}

spawn_sandboxed(compile_sandbox, "bash", "-c 'gcc -o build/app src/*.c'")
spawn_sandboxed(deploy_sandbox, "bash", "-c 'scp build/bin/app deploy.internal:/opt/'")

Each bash step inherits LD_PRELOAD. Every external command that bash spawns (gcc, scp, curl, cat) is sandboxed, checked against the step's grants.

Why builtins don't matter

The builtin gap sounds alarming but isn't a practical concern:

  • echo doesn't access protected resources. It writes to stdout. If stdout is a terminal, the output is visible to the user who launched the sandbox, not an escalation.
  • read < file is a concern in theory, but bash scripts that read files almost always use cat or other external commands which ARE sandboxed.
  • /dev/tcp is the real risk, bash can open TCP connections without an external command. However, /dev/tcp is a compile-time option in bash and is disabled in many distributions (Debian, Ubuntu disable it by default).

The Docker analogy

This is the same model as Docker. A Docker container doesn't restrict what the shell does internally, it restricts what resources are mounted and what network is available. Bash can echo all it wants inside a container. It can't curl to a host that isn't in the container's network.

Aether's sandbox is the same: bash runs freely inside the permission boundary. The boundary is what matters.

Not recommended: forking bash

Forking bash (~140K lines of C) to add sandbox checks to builtins is technically possible but creates a maintenance burden. Every bash security patch requires a rebase. Users won't install a custom bash. The LD_PRELOAD model with external command interception is the practical approach.

Not recommended: rbash

Bash's restricted mode (rbash) disables cd, PATH changes, and redirections. It solves a different problem, restricting the user FROM bash features, not restricting bash's access to resources. It's not a substitute for sandbox grants.

Cross-process containment (future)

Implementation sketch

The preload library (libaether_sandbox.so) would be ~200 lines of C:

// libaether_sandbox.so, LD_PRELOAD interception

#include <dlfcn.h>    // dlsym for real libc functions
#include <sys/mman.h> // shared memory for grant list

// Load grants from shared memory (written by Aether parent)
static grant_list* grants = NULL;
static void __attribute__((constructor)) init() {
    int fd = shm_open("/aether_sandbox_PID", O_RDONLY, 0);
    grants = mmap(...);
}

// Intercept connect()
int connect(int fd, const struct sockaddr* addr, socklen_t len) {
    char* host = resolve_addr(addr);
    if (!check_grant(grants, "tcp", host)) {
        errno = EACCES;
        return -1;
    }
    return real_connect(fd, addr, len);  // dlsym(RTLD_NEXT, "connect")
}

// Intercept open(): a read needs fs_read, a write fs_write, O_RDWR both
int open(const char* path, int flags, ...) {
    int acc = flags & O_ACCMODE;
    int reads = acc == O_RDONLY || acc == O_RDWR;
    int writes = acc != O_RDONLY || (flags & (O_CREAT | O_APPEND | O_TRUNC));
    if ((reads && !check_grant(grants, "fs_read", path)) ||
        (writes && !check_grant(grants, "fs_write", path))) {
        errno = EACCES;
        return -1;
    }
    return real_open(path, flags, ...);
}

// Intercept getenv()
char* getenv(const char* name) {
    if (!check_grant(grants, "env", name)) return NULL;
    return real_getenv(name);
}

The grant checking logic is identical to the in-process checker, same glob patterns, same prefix/suffix matching. One codebase, two enforcement points: in-process (stdlib checks) and cross-process (LD_PRELOAD).

Why doPrivileged is unnecessary

Java's AccessController.doPrivileged() let contained code temporarily escalate permissions to perform a privileged operation:

// Java: restricted code escalates to read a file
AccessController.doPrivileged(() -> {
    return new FileInputStream("/etc/app/config.yaml");
});

This was a containment violation by design, the contained code reaches upward for capabilities it shouldn't have.

The IoC / Dependency Injection pattern (originating with Stefano Mazzocchi's Inversion of Control in Apache Avalon, later refined in PicoContainer, Spring, and others) eliminates the need entirely. The container does the privileged work and injects the result into the contained, as a constructor argument, a closure parameter, or a service interface.

The injected dependency isn't limited to read-only data. It can be a service with full business logic, including mutation:

// Container: has full access, creates a database service
db = connect_database("/etc/app/db-config.yaml")

// The db service has methods: query, insert, update, delete
// It encapsulates the privileged connection, the worker never
// sees the filesystem or raw TCP

worker = sandbox.new("worker") {
    // No grant_fs_read, no grant_tcp, worker can't touch either
    // But it CAN use the db service that was injected
}

sandbox.enforce(worker) callback {
    // Worker calls db.query(), db.insert(), business logic with
    // mutation, not just read-only data. The privileged connection
    // is behind the service interface. Worker never escalates.
    result = call(db_query, db, "SELECT * FROM users")
    call(db_insert, db, "INSERT INTO logs VALUES (...)")
}

The contained code has no filesystem access, no TCP access, but full database read/write capability, because the container injected a service that encapsulates the privilege. The privilege boundary is the service interface, not a doPrivileged escalation.

What makes this work is when the privilege was used. The checks sit where authority is acquired (opening a path, connect, exec, getenv), and inside sandbox.enforce every acquisition is checked, by whatever code makes it, wherever that code was defined. db connected before the block, so using the connection inside needs no grant. A db_query that opened a new connection on each call would be refused like any other code in the block: a function does not carry the authority of the place it was written, only of the resources it already holds.

When the container wants a function to keep its own authority inside the block, it says so at the enforce, by name:

sandbox.enforce(worker, audit_log, db) callback {
    audit_log("job started")     // trusted: the container's authority
    rows = db.query("...")       // trusted: every call into module db
    fs.read("/etc/shadow")       // still refused
}

This keeps the property that made doPrivileged unnecessary. The exemption is granted by the container, in the container's code, at the point it hands the work over; contained code cannot claim it. Concretely:

  • A trusted call's authority is the sandbox levels in force when the enforce was entered: it pushes a barrier hiding the levels from that enforce up, so an enforce the trusted function writes itself stacks above the barrier and cannot disturb the block's grants. Contained code that writes its own enforce(everything, peek) enters it already sandboxed, so a call it trusts drops back no further than the sandbox it is in.
  • Trust is lexical. It covers calls written in the block (and nested blocks and closures written there), not a function called from elsewhere that happens to call audit_log, and the names cannot be used as values in the block, so they cannot be passed on.
  • The trusted call's arguments are evaluated inside the sandbox; only the trusted function's own body runs outside it. audit_log(fs.read(secret)) still has the read refused.
  • Only Aether functions can be trusted (each gets a generated wrapper with its exact signature), not C externs.
  • A panic that unwinds through a trusted call, or out of the block, puts the depth back where the catching try found it.

The mechanism lives in the compiler (compiler/analysis/sandbox_trust.c and the trusted-call wrappers in compiler/codegen/codegen.c), beside the sandbox_push / sandbox_pop builtins the sandbox already rests on.

This is the IoC principle applied to sandboxing: inject capabilities, don't let the contained reach for them.

Data exchange: shared map

Aether and hosted languages exchange data through a token-guarded string:string map. All values are strings. The map has function call semantics, inputs flow in, outputs flow out. It is not a bidirectional messaging channel.

Contract

        Aether          │         Hosted Code
                        │
  map_put("input", x)   │
  map_put("config", y)  │
        ── freeze ──────┤
                        │  map_get("input")  → x  ✓
                        │  map_get("config") → y  ✓
                        │  map_put("input", z)    ✗ (frozen)
                        │  map_put("result", r)   ✓ (new key)
        ── return ──────┤
  map_get("result") → r │
  map_revoke_token()    │
  map_free()            │

How it works

  1. Aether creates the map and puts input key-value pairs
  2. Inputs are frozen before hosted code runs, hosted code can read them but cannot overwrite them
  3. Hosted code writes outputs as new keys via aether_map_put
  4. Hosted code returns, Aether reads output keys
  5. Token is revoked, the map is inaccessible from the hosted side
  6. Aether frees the map when done

Token guard

The map is accessed from hosted code via a one-time token. The token is generated randomly, validated on every get/put, and revoked after the hosted code returns. A stale or guessed token returns nothing.

Native bindings

Each host bridge provides two bindings to the hosted language, aether_map_get(key) and aether_map_put(key, value): stunt's map-* checks here, and the Lua, Python, Duktape, QuickJS, Perl, Ruby and Tcl bridges of aether-guest-languages under the same names (the Rexx bridge spells them AETHER_MAP_GET and AETHER_MAP_PUT).

Example

With the Duktape bridge of aether-guest-languages (import duktape there):

import duktape

worker = sandbox.new("worker") {
    grant_env("HOME")
    grant_fs_read("/etc/*")
}

// Create map with inputs (std.sharedmap)
map = sharedmap.new()

_p2 = sharedmap.put(map, "threshold", "42")

// Run JavaScript, it reads inputs, writes outputs
duktape.run_sandboxed_with_map(worker, <<JS
    var user = aether_map_get("user");
    var threshold = aether_map_get("threshold");
    aether_map_put("result", "processed " + user);
    aether_map_put("count", "1000");
JS
, token)

// Read outputs
result, _f1 = sharedmap.get(map, "result")
count, _f2 = sharedmap.get(map, "count")

sharedmap.free(map)

Type convention

All values are strings, carried by their length: a NUL inside a key or a value is a byte like any other, in the map and in the shared memory block a sandboxed child reads (layout 2, length-prefixed, with a magic and a version; runtime/aether_shared_map.h). Numbers, booleans, and other types are encoded as strings by the sender and parsed by the receiver:

_a = sharedmap.put(map, "threshold", "42")      // int
_b = sharedmap.put(map, "rate", "3.14")         // float
_c = sharedmap.put(map, "enabled", "true")      // bool
_d = sharedmap.put(map, "tags", "a,b,c")        // list (caller's convention)
local threshold = tonumber(aether_map_get("threshold"))  -- 42
local rate = tonumber(aether_map_get("rate"))             -- 3.14
local enabled = aether_map_get("enabled") == "true"       -- true

This is the same convention as HTTP headers, environment variables, and command line arguments. Every cross-boundary interface in computing passes numbers as strings. The sandbox boundary is no different.

Nested maps

The shared map is flat by design. Use dot-delimited keys when you need hierarchy:

db.host = localhost
db.port = 5432
db.credentials.user = admin

The hosted code splits on dots if it wants to reconstruct a tree. The map stays a single-level key-value store, simple, auditable, and with no deserialization attack surface.

Future: string:bytes mode

A flag on shared_map_new() will switch values from null-terminated strings to length-prefixed byte arrays. Same API, same token guard, same freeze/revoke lifecycle. For binary data too large to base64.

How Aether compares to other capability / sandbox systems

Aether's capability model runs at three levels and composes with bidirectional host-language interop. Useful to anchor against systems readers already know.

Three enforcement layers

  1. Module boundary, under --emit=lib the compiler rejects imports of std.fs, std.net, std.os at build time; the host opts each one in with --with=fs[,net,os]. See emit-lib.md.
  2. Scope boundary, hide <names> and seal except <allowlist> let any lexical block (closure, trailing-block DSL, actor handler) decline to see selected enclosing names; reading, assigning, or re-declaring a hidden name is a compile error, and the denial travels with the block. See hide-and-seal.md.
  3. Runtime process boundary, libaether_sandbox.so (LD_PRELOAD) intercepts libc (open*, connect / bind / accept, execve / fork, mmap / mprotect, dlopen, getenv) against a builder-DSL grant list, inherited across execve. Covers normal-libc code. Adversaries using openat2 / io_uring / sendfile / execveat / raw syscall() / ptrace bypass it (enumerated in detail above under Interception surface).

Bidirectional host interop

Aether plays either side of the embedding relationship, with the same permissions registry and LD_PRELOAD checker either way.

  • Aether as guest, a host-language app loads an Aether .so built via --emit=lib, which carries a typed namespace manifest (aether_describe()) used by ae build --namespace to generate per-language SDKs. Shipped: Python (ctypes), Java (Panama, JDK 22+), Ruby (Fiddle). Go stubbed. Host-side is normal methods, no JNI, SWIG, MemorySegment, or ctypes.CDLL boilerplate. Callback model is Hohpe's claim check: script emits notify(event, id), host calls back through the typed downcall API for detail. See embedded-namespaces-and-host-bindings.md (typed-SDK story) and aether-embedded-in-host-applications.md (rationale + YAML/HCL/Pkl/Jsonnet/Starlark comparison), and aether-vs-hcl.md for HCL side by side.
  • Aether as host, an Aether main() executable runs <lang>.run_sandboxed(perms, code) for Lua, Python, Perl, Ruby, Tcl, JavaScript and more in-process, through the bridges of aether-guest-languages (ae add it, then import <lang>). Java, Go, and aether-hosts-aether (contrib.host.aether, still in this tree) are separate-process (Aether is compiled, so aether-hosts-aether uses fork+exec with LD_PRELOAD on the child). hide / seal except are Aether compile-time constructs, they do NOT travel into hosted non-Aether interpreters, which have their own scoping; containment for those is grants + LD_PRELOAD only. hide / seal except still shape the Aether-side grant-assembly block and the hosting closure. See each language's README in aether-guest-languages and contrib/host/TODO.md.

What it's most like

  • Pony object capabilities, closest analogue in a systems language. Aether's grants are coarser (stdlib category at the module level, name at the scope level, libc entry point at the runtime level); Pony attaches capability modes to individual references.
  • Java's removed SecurityManager, same structural idea (java.policy grants, AccessController.doPrivileged), same layer (interpreter / VM-level check on sensitive operations). Deprecated in JDK 17, removed in JDK 24 because the maintenance cost outgrew the benefit in an ecosystem where most applications trust their dependencies. Aether's equivalent survives because the scope is narrower (the grant list is populated by a builder DSL in the same codebase, not by a system-wide policy file parsed from XML) and the enforcement point is libc, not the VM.
  • A fraction of gVisor, both intercept at a boundary (gVisor's Sentry emulates syscalls; Aether's LD_PRELOAD wraps libc). gVisor is kernel-level (process-scoped, every syscall) and handles adversarial workloads. Aether is userspace-level (libc-scoped, easily bypassed by raw syscall()) and handles cooperative containment. gVisor gives you a hardened sandbox for untrusted containers; Aether gives you a developer-ergonomic permission surface for trusted-but-sandboxed plugins.

What it is NOT

  • NOT Ruby / Smalltalk / Groovy's builder-style closures, those languages interpret the trailing block at runtime with full access to the interpreter's reflection surface. Aether compiles the closure to C; the sandbox grant list is the compiled function's only handle to privileged operations. hide / seal except are checked by the compiler, not by a runtime SecurityManager.
  • NOT a runtime wrapper (WASI, gVisor, Firejail), --emit=lib changes what the compiler will emit at all, not what the runtime will permit later.
  • NOT a library flag (Deno's --allow-net, Node's experimental permission model), those are process-wide allowlists checked at API call sites. Aether's gate is at compile time and at scope entry, plus an optional runtime check.
  • NOT an annotation convention (Rust crates, Go build tags), those require ecosystem buy-in and don't prevent a dependency from pulling in what it needs. Aether rejects the import.

What's novel is the combination

Most embeddable languages (Lua, Wren, Starlark, Hermes) give you the embedding but leave capability management to the host. Most capability-secure languages (Pony, E) don't ship polyglot SDK generators or in-process interpreter bridges. Aether bundles both directions (guest + host) behind one permissions model.
